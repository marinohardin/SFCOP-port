# src/app/guest: the guest host

Runs the lifted game as a component of the client (DESIGN §7.3). `main.cpp` constructs the
platform components and calls `guest::Run()`; the host attaches the HLE modules to those
components, maps the original exe, binds its imports, and enters the C runtime's start-up, which
calls `WinMain`. The host is built only with the lift and never compiles `game/`.

| File | What it does |
|---|---|
| `GuestHost.h`, `.cpp` | `Run()`: the modules attached to the components, the exe mapped and bound, static TLS, the event pump, the watchdog, the exit |
| `GuestPump.h`, `.cpp` | The event pump, bound to the main thread: any other thread that peeks a message does not read the window's events; its turns for a message and inside the game's calls, the frame rule, the gaps between turns |
| `GuestShots.h`, `.cpp` | `--shots DIR --shot-every S`: the back buffer read through `Gpu::ReadTexture` into a 24-bit BMP (the format `framediff.py` reads) |
| `FaultClass.h`, `.cpp` | Which hardware faults become guest exceptions: the pc must lie in lifted code (or a leaf memory routine it calls) |
| `GuestExceptions.h`, `.cpp` | The landing pads the lift's code pushes and pops, the two transfers the lift calls (`_JumpToContinuation`, the `__except` call), and hardware faults raised as guest exceptions |
| `GuestGame.cpp` | What is the original's own: the OSSpecific DLL it loads, the marks, B9's override table written into the dispatch table (below) |
| `override.*` | B9's: the table of game functions that run as source instead of as lifted code |
| `tests/` | The guest tests: a VC6 test program lifted and run on this host (below) |

## How a run goes

1. The kernel32rt runtime is attached to `Threads` and `Clock`, the kernel and registry modules
   to the install and the data folder, DirectInput to `Input` and `Threads`; with a window, the
   DirectDraw module to `Gpu` and `Window`.
2. The modules' tables are registered (`sfcop_register_hle_modules()`, generated by the build),
   then the game's own rows (`GuestGame.cpp`).
3. The exe is mapped at 0x00400000 and its imports bound. An import a module answers goes to it.
   One no module owns goes, in this order, to the P1-2 spike's stubs (TEMPORARY,
   `src/app/boot/misc_stubs.c`) or to pcrecomp's win32hle, through a wrapper that logs
   `[guest] NAME: answered by ... (no module owns it)` at its first call. The bind lists them all
   (`[guest] imports answered by ...`). An import nothing answers ends the run, naming itself, when
   it is called.
4. With `--dry-run` the run stops here. Otherwise the window is opened (not with `--headless`,
   whose stub Window and Gpu draw nowhere), the pump and the watchdog start, and the main thread
   enters the exe's entry point.
5. `ExitProcess` ends the process with the client's exit code: 0 for 0, else 1 (DESIGN §6.8).

## Threads

The game's own threads stay as they are. `CreateThread` starts a `Threads` thread for each, with a
16 MB host stack; one machine lock lets one thread run guest code at a time, and every blocking
call (a wait, `Sleep`, a held critical section, stopping a multimedia timer) gives it up for its
length. Imports and loop back edges are hand-over points too, as a processor quantum ends on
Windows. A waiting thread gets the machine only once the running one has passed its quantum of
them since it took the machine, a count of the guest's own steps, never host time. A loop that
ran a back-edge interval without calling any import is spinning on a lock or a flag, and hands the
machine over at once. The thread that calls `Run()` is the game's main thread and the platform's: the window's
events are pumped there whenever the game's message queue runs empty (`PeekMessage`,
`GetMessage`; from any other guest thread the call does not read the window). The pump is the one
place the `Window` is drained: each event goes to the user32 module's message queue
(`hle::user32::AttachHost`, called once in `Run()` before guest code), which turns keys, the mouse,
focus and the close box into the game's messages (`WM_CLOSE` included). A main thread blocked in a
long wait does not pump.

**The pump inside the game's calls.** A load that never peeks (the boot's splash, the campaign's
progress screen, a saved campaign's load) would leave the window's events unread for seconds, and
macOS shows the busy cursor after about two. So, when the turns inside calls are on (below), the
bind gives every import of the kernel, kernel32rt, registry, Miles, DirectSound3D and GDI modules,
and every import no module owns, a row of its own that may run a turn of the pump inside the call:
`EventPump::PumpInsideCall`, on the main thread only, once at least 50 ms have passed since the
last turn of either kind. Each wrapped row of a module has a slot of its own (no lookup per call);
an import no module owns still finds its row by name on every call (a string copy, a map find and
a set insert), exactly as on develop, and pays the counter on top. On the main thread the clock is read before every 16th wrapped call, and before and after every row that may
block by itself (`Sleep`, the waits, `LoadLibraryA`, `CopyFileA`, opening the sound device), so
the millions of short calls a second the game makes in play pay a counter, not a clock read. When
the turns are off and no gap trace is asked for, no row is wrapped and the bind is as it was.
Such a turn reads the window's events and hands them to the user32 module's queue, nothing else:
no frame, no DirectInput work, no shot, no call into the game. The game receives them at its next
`PeekMessageA` or `GetMessageA`, in the order the window reported them, and the messages carry the
time they were queued. Mouse moves the game has not read yet coalesce into the latest, as on
Windows; buttons and keys are kept, so a click made during a load reaches the game when it next
reads its queue, as on Windows (`hle/user32/README.md`). USER32's own rows pump already and are
not wrapped; an import found through `GetProcAddress` runs without it.

The wrappers rely on pcrecomp's shim registry (`runtime/win32hle/host_lite.c` at the pinned
revision). A row's address is `SHIM_BASE + 16 * index`, indexes are handed out without a gap, so the
bind finds the wrapper it has just registered by a binary search with `hle_name`, which answers null
for an address no row has. `hle_resolve(name)` scans from the first row and returns the first match:
the module's row, registered before the wrapper of the same name, still answers (that is why a
`GetProcAddress` import runs unwrapped). The registry holds `MAX_SHIMS` = 2048 rows and cannot refuse
one: `win32hle_register` ends the run ("too many shims") past it. So the bind registers a wrapper
only while 128 rows stay free for the tables registered after the bind; an import that finds no room
keeps its module's row (a line says so) and runs without the pump. With the turns on the registry
holds 1,436 rows (1,230 without).

The rule: the turns inside calls run only when `Options::pumpDuringLoads` is set, and never
headless. `main.cpp` clears the flag for `--input`, `--oracle`, `--record-trace` and `--headless`
(each says so in `--help`): an input script counts every read of the window as one of its frames
(`app/input/ScriptedWindow.h`) and clicks after a number of them, and the oracle's traces count
them too, so every scripted, recorded or headless run reads the window only when the game peeks,
exactly as before. `--fixed-step` alone does not clear it: it is a clock mode, and the turns
inside calls never count as frames. The rule is `app::readsWindowDuringLoads` (`CommandLine.h`).
The proof of the turns inside calls is therefore a run driven by hand.
For measuring, `SFCOP_PUMP_INSIDE_CALLS=0` turns them off for any run and `=1` on for any
run, headless included (where it reads nothing and measures the cost), whatever the flag; a
scripted run's frames then differ from develop's.

`SFCOP_PUMP_TRACE=<ms>` logs each gap of at least that many milliseconds between two turns on the
main thread (400 lines at most), with what the main thread spent it in: the wrapped rows it
called, their counts and time (inclusive of what they called back), and the rest, the game's own
code; and, at the end of the run, the counts of turns and the longest gap.

A message turn of the pump that read no event from the `Window`, with no turn inside a call
having read one since the message turn before it, is a frame: the game's message queue is
then empty and the game runs one. `Options::onFrame`, when the client sets it, is called on the
main thread after each such turn; `--oracle`, `--record-trace` and `--fixed-step` advance the
fixed-step clock there (`platform/Clock/FixedStepClock.h`) and then fire the multimedia timers it
has made due (`hle/kernel32rt/Timers.h`). `EventPump::FrameEnded()` is the rule. A turn that read an event, the
operating system's or an input script's, is not one, and a turn inside a call never is, so the events only a window receives (shown,
exposed, focus) do not change the count of frames.

## The working directory

The process runs from the per-user data folder, never the install, which is never written. The
game's own relative names are the kernel module's (it keeps a virtual current directory). Of the
137 imports no module owns, none opens a file by a relative name except `CreateFontA`
(pcrecomp's `gdidc.c`), which looks a font up by name and only reads: a relative name resolves
against the data folder. `CreateFileMappingA` and `MapViewOfFile` work on a handle the file rows
gave (a duplicate of its descriptor, or anonymous memory); `OpenFileMappingA`, `OpenProcess`,
`CreateProcessA`, `WinExec` and the file dialogs refuse or answer "cancelled" without touching a
path. The proof keeps the install-unchanged check: after a boot on a clone of the install,
`find "$GAME" -newer "$STAMP"` lists no file (stamp made before the run).

## Exceptions

A guest exception (`RaiseException`, a C++ `throw`, an access violation, a divide by zero) is
dispatched over the guest's own `fs:[0]` chain by `hle/kernel32rt`'s dispatcher, so the game's
handlers decide, as on Windows. A catch or an `__except` block is entered by a `longjmp` to the
landing pad of the function that owns it (`cmake/lifter/run_lift.py` gives every such function one
and lists every continuation in `recomp_eh_table.c`); the pad restores the machine lock's depth it
had, so a throw across a system callback (a native call into guest code that never returned)
leaves the lock as it was. A hardware fault in guest memory becomes `EXCEPTION_ACCESS_VIOLATION`
with its read or write flag and address, but only when the faulting instruction is lifted code
(the span of the dispatch table's functions) or a leaf `memmove`/`memcpy`/`memset` it calls: the
exception is a `longjmp` over every frame in between, which is sound over lifted C and not over
host frames holding locks or strings. A fault in other host code (a module touching a guest
pointer it did not check) is a host defect: it is reported with the pc and the guest address and
ends the run. The read or write flag comes from the fault context on Apple silicon, macOS x86-64
and Linux x86-64 (`REG_ERR`); elsewhere it is unknown and recorded as a read. The span's end is
the last function's start plus 32 KB, and a host function inside the span would count as lifted.
The pads save and restore no signal mask: a POSIX host takes `_setjmp` and `_longjmp`
(`cmake/lifter/patches/pcrecomp-eh-setjmp.patch`), as `setjmp` saves the mask with a system call on
every entry to a function with a pad; a Windows host keeps `setjmp` and `longjmp`. The fault
handler adds nothing to the mask (`SA_NODEFER`). On macOS a `_longjmp` out of a signal handler
would leave the thread marked as on its alternate stack, so a jump to a pad older than the fault
first returns into the handler, which then returns from the signal into a short function that
makes the jump. That function runs on the stack the handler ran on (the alternate stack), below the
handler's finished frames, never below the faulting stack pointer, where a thread whose stack is
nearly used up has no room. A pad pushed while the handler runs (by a function a catch block calls)
is reached directly, and the handler's record stays in place for the next jump to an older pad;
Linux needs no such step.
A fault in lifted code with the chain damaged ends the thread as unhandled; a zero divisor becomes `EXCEPTION_INT_DIVIDE_BY_ZERO`
(`cmake/lifter/patches/pcrecomp-div-fault.patch`). A handler that asks to continue after a fault
cannot retry the access: the run stops there. An exception no frame takes is reported on stderr
with the chain, then the program's top-level filter runs, as on Windows.

## Tests

The guest tests run `tests/ehtest.cpp`, built by VC6 SP4 with `/GX` and the static C runtime and
lifted by the same driver as the game, on this host (`tests/GuestTestMain.cpp`: the real `Threads`
and `Clock`, stubs for the rest). Twenty-two cases each print `PASS` or `FAIL`: C++ throws by value,
by reference, nested, rethrown, thrown from a catch, unwinding two frames, 100 in a loop, every
exception object destroyed; `__try`/`__except` around `RaiseException`; static TLS and a throw
caught on a second thread; thread ids that are never 0 and differ per thread; a critical section
left free by a thread that ended inside it, by returning or through `ExitThread`; access violations caught by `catch(...)` and by `__except`, with a read
and a write told apart; 20 access violations in a row on one thread, each rethrown from its
`catch(...)` to an outer catch; faults inside a fault's catch block, caught in a function the block
calls and by the outer `try`, then one more fault after them; a throw out of a system callback with the lock depth unchanged; a divide by
zero caught by `__except`; 300 `TlsAlloc`/`TlsFree` pairs, which fail when a module's `TlsFree` is not answered by kernel32rt. A second run throws an `int` nothing catches: it is reported, and the C
runtime's own filter ends it with `abnormal program termination`. On a POSIX host the test also
counts the 28 access violations' report lines, each of which says whether its handler ran on the
main thread's alternate signal stack, and fails unless all 28 did; on macOS it also needs one
return into an older frame per fault, each on the alternate stack. The counts are at the top of
`tests/run_ehtest.sh`; a new fault case changes them.

A new case that expects a `catch` or `__except` to take a fault needs a call in its `try` that the
compiler cannot see through. VC6's `/GX` drops a `try` block whose calls it can see never throw: a
store through a pointer in a small `static` function called directly is such a call, and the case
then has no handler at all (`case_fault_twice` calls through a function pointer for this reason).
Taking the address of a function the other cases call directly can change how those cases are
compiled too, so give a new case its own function. `llvm-objdump -d -r` on `ehtest.obj` shows
whether a case function still links a record into `fs:[0]` (`__except_list`).

    cmake --build <build> --target sfcop_ehtest_lift   # VC6 compile and lift; sets SFCOP_ROOT itself
    cmake <build>                     # the sfcop_guest_tests target appears once the lift exists
    cmake --build <build> --target sfcop_guest_tests -j4
    ctest --test-dir <build> -R sfcop_guest_tests

Without the VC6 toolchain container or the lift, the target and the test are absent, and
configuring says `sfcop_ehtest: skip: ...`; the doctests
of `hle/kernel32rt` and of `Clock` and `Threads` run in `sfcop_tests` everywhere. Set
`SFCOP_GUEST_TRACE=1` to trace a run of the test host.

The machine's hand-over rule (Threads, above, and `cmake/lifter/patches/pcrecomp-quantum.patch`)
has its own test, `tests/MachineQuantumTest.cpp`. It builds pcrecomp's `host_lite.c` from a
patched copy (`cmake/lifter/patches/series` applied) and needs no lifted program. A thread keeps the machine through its quantum of imports while
another waits. The import that ends the quantum hands the machine over, and a new quantum starts
when the thread takes it back. A yield hands it over at once, and so does a back-edge hook with no
import by its own thread since that thread's last hook. Every build with the lift has it as the
CTest test `sfcop_machine_quantum_tests`, compiled against the build folder's patched copy.
Without a build, the script below takes the pcrecomp clone, only reads it, and makes its own
patched copy in the scratch folder (`setup.sh --copy`) to build against:

    ctest --test-dir <build> -R sfcop_machine_quantum_tests
    sh src/app/guest/tests/run_machine_quantum.sh <pcrecomp clone> <build>/_deps/doctest-src <scratch dir>

## Indirect calls

Every indirect call of lifted code (a virtual call, a function pointer, an import through its
IAT slot) asks three lookups: the dispatch table, the host's manual hook and the import shims
(`cmake/lifter/patches/pcrecomp-dispatch-cache.patch`). The table answers from a direct-mapped
cache of 16,384 slots in front of its binary search, misses included, so an import's address,
which is never in the table, is not searched for again. Each slot is one 64-bit word holding the
address and the table index, read and written whole.

The order depends on whether the host has folded its own functions into the table:

- **Not folded** (any host that never calls `hle_dispatch_fold`): the hook, the table, the
  imports, as before the patch. A hook that supplies a function in place of a lifted one at the
  same address must be asked first, or the lifted one would run.
- **Folded**: the table, the hook, the imports. `hle_dispatch_fold` sets
  `recomp_dispatch_folded`, which the call macros read.

At start-up `GuestGame.cpp` writes B9's override table into a copy of the dispatch table
(`hle_dispatch_fold`): an override at an address the table holds replaces that entry, one at a new
address is added. The manual hook then answers only the missed constructor (0x0059644A, run by the
lifted 0x004014A9) and, through the mission modules' loader, the modules' own addresses: neither is
in the table, so asking the table first changes no answer. Before guest code runs, every address of
the generated table, every override and the missed constructor is asked twice (once from the
search, once from the cache) and compared with what the old order (override table, hook, table)
found; a difference ends the run, naming the address. It takes about 10 ms on an M1 Pro.

The fold is for start-up only, before any guest thread runs: a lookup on another thread during a
fold could pair a cached index with the wrong table. A previous copy of the table is never freed.

The cache, the fold and both orders have their own cases in `tests/MachineQuantumTest.cpp`, in the
same CTest test: the generated table's one entry, entries folded in and a cached miss found after
the fold, a replaced entry, 40,000 entries against the 16,384 slots in three orders, two threads
reading at once, and an indirect call (`RECOMP_ITAIL`) to an address both the table and the hook
answer, before a fold (the hook's function runs) and after (the folded one).

## Results (macOS arm64, 2026-11-04, fix round 1)

**Platform.** Every result below was produced on macOS arm64 only. The Linux and Windows presets
are stub toolchains (they configure and build nothing), so the guest tests are not proven there;
the brief's "all three presets" is not met and cannot be yet. The Linux backend files
(`HostMemory_linux.cpp`, `ThreadsHost_linux.cpp`, the `REG_ERR` read) are written but unrun.

| Headless boot, clock 15:38 (`space21`), watchdog 60 s | the CD-key prompt at 10.1 s; exit 0; 1230 of 2048 shim slots in use |
