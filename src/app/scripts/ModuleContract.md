# The mission module contract

What a native mission module is, and what the native build checks before it runs one (DESIGN §5.9
path (b), §6.4, §9). `scr2native` (`tools/scr2native/README.md`) produces modules to this contract;
the loader (`ModuleLoader.h`) refuses anything else. Contract version **1**
(`kModuleContractVersion`).

The 32-bit Windows build does not use this contract: it loads the original `.scr` files as the
original game does (DESIGN §5.9 path (c)).

## 1. Entry points

A module exports the two functions the scripting library defines in every original mission, with C
linkage and the platform's default C calling convention, under their plain C names (`MissionSpecEntry`
and `ScriptEntry`; on Mach-O the object format adds its leading underscore as for any C name):

| Export | Signature, as the scripting library declares it | Purpose |
| --- | --- | --- |
| `MissionSpecEntry` | `extern "C" const tMissionSpec* MissionSpecEntry(float Version)` | The mission's specification for the mission lists and the server. Returns null when `Version` is not the library version the module was built for |
| `ScriptEntry` | `extern "C" tScriptEntry* ScriptEntry(void)` | The script interface the game drives the mission through: the `tScriptEntry` virtual table, then the callbacks the game installs through it |

In the original these are `__cdecl` and exported as `MissionSpecEntry` and `ScriptEntry` from the
`.scr`; the 64-bit hosts have one C calling convention. `tScriptEntry` and `tMissionSpec` are the
scripting library's types, declared by its headers in the SDK; this repository does not hold those
headers (DESIGN §12.5), so `ModuleLoader.h` only declares the two names and the function types:
`MissionSpecEntryFn` and `ScriptEntryFn`.

## 2. Version tag

A module exports a data symbol `sfcop_module_abi` (C linkage) of type `ModuleAbiTag`:

| Field | Type | Value |
| --- | --- | --- |
| `magic` | `char[8]` | `SFCOPMOD`, no terminator |
| `contractVersion` | `uint32_t` | `kModuleContractVersion`, the version of this document |
| `scriptVersion` | `float` | The scripting library version the module was compiled against: `kScriptVersion`, the SDK's `kCurrentScriptVersion` (22.0) |
| `compilerAbi` | `char[32]` | The host ABI the module was compiled for, NUL-terminated: `kHostAbiTag` of the build that made it |

`kHostAbiTag` is `<architecture>-<system>-<C++ ABI>`: `arm64-macos-itanium`, `x86_64-macos-itanium`,
`x86_64-linux-itanium`, `arm64-linux-itanium`, `x86_64-windows-msvc`. The tag holds no pointer, so
the loader reads it from the file without loading the module. All four fields must equal the
loader's own values; anything else is refused.

## 3. Imports

The module's imports are the undefined dynamic symbols its file records (Mach-O and ELF symbol
tables, the PE import table), read from the file before any of its code runs.

1. **The scripting library and the C runtime.** An import named `sfcop_import:<name>` binds to
   `<name>` of the original's scripting library or C runtime, which the native build exports under
   that prefixed name. `<name>` is the original's name for the symbol, as the VC6 build of a mission
   sees it: the decorated name for a C or C++ symbol (`?mAssessDamage@tShipInfo@@QAEJW4eRace@@@Z`, `_atexit`)
   and `DLL!Name` for a Windows import (`KERNEL32.DLL!HeapAlloc`). `<name>` must be on
   `allowlist.txt`.
2. **The host's own runtime.** Every other import (the compiler support routines a host compiler
   emits, such as `memcpy` or `__stack_chk_fail`) must be on the host baseline list for the
   platform. That list belongs to the real loader and is generated from the host toolchain the
   same way as `allowlist.txt`; while it is empty, every such import is refused.

The prefix keeps the two name spaces apart: `_free` in the original is the C runtime's `free`,
while `_free` in a Mach-O file is the host's.

**The allow-list** is `allowlist.txt` beside this file, generated by `tools/scr2native/gen_allowlist.py`
from the install at build time and never typed. Lines starting with `#` are the header (generator,
SDK version, scripting library version, the library's hash, part counts, and how many references
the template's link left unresolved and were dropped); every other line is one
symbol, sorted by byte value, each once. It is the union of:

| Part | What |
| --- | --- |
| library | Every external symbol a member of the SDK's `ScriptInterfaceR.lib` defines |
| linked | The symbols the Single template's objects and the `ScriptInterfaceR.lib` members reference and that the template's link resolved in another SDK library (SharedR, sfcTiger, dmp3D and its stand-in) |
| runtime | The same references resolved in the VC6 C and C++ runtime (LIBCMT, LIBCPMT) |
| imports | The PE import table of the Single template built with VC6 SP4, as `DLL!Name` |

Compiler-generated names that no module imports (string literals, floating-point constants,
dynamic initializers, throw descriptors) are left out. The Single template is the SDK's own
starting point for a mission, so its link is the reference for what a mission uses beyond the
library itself.

The check names the first import in the module's own order that fails it, a library import by
its original name without the prefix. `gen_allowlist.py
--check <imports>` applies rule 1 to a list of names (one per line) and names every one that fails.

**Dynamic lookups.** The C runtime needs `KERNEL32.DLL!LoadLibraryA` and
`KERNEL32.DLL!GetProcAddress`, so they are on the allow-list; through them a module could reach
any function by name. The loader's binding shims for `LoadLibraryA`, `LoadLibraryExA`,
`GetModuleHandleA` and `GetProcAddress` therefore resolve only names that are on the allow-list,
and only against the modules the allow-list names (the `DLL` of its `DLL!Name` entries) and the
module itself:

- A module name is compared upper case, without its directory, with `.DLL` added when it has no
  extension (`C:\WINDOWS\system32\kernel32` is `KERNEL32.DLL`). A null name is the module itself.
- `LoadLibraryA`, `LoadLibraryExA` and `GetModuleHandleA` succeed only for a module the
  allow-list names, or the module itself.
- `GetProcAddress` succeeds only for `DLL!Name` on the allow-list (an ordinal is `DLL!#n`, and
  none is on it), or for an export of the module itself.
- The game's own libraries count as the modules the allow-list names: `OSSPECIFIC95.DLL` and
  `OSSPECIFIC98.DLL` load, and `GetProcAddress` answers their one entry on the list with the
  client's implementation. A name the allow-list leaves out is answered 0, never a stub: the
  module's own fallback runs, as it would on a system without the function.

A lookup of anything else returns null, as the Windows call does when it fails, and is refused
with the message of a direct import, naming the symbol (`DLL!Name`; the module name alone when a
module lookup names a module the allow-list does not name; the plain export name for the module
itself): `refused: <m>: imports KERNEL32.DLL!CreateProcessA, which is
outside the scripting library and the C runtime`. `checkDynamicLookup()` and
`ModuleLoader::checkLookup()` make this check; A3 tests the shims against it.

## 4. Files

A module is a directory under the modules root, named after the original `.scr` without its
extension (`Ski_1Free4All/`), holding:

| File | What |
| --- | --- |
| `<Name>.dylib`, `<Name>.so` or `<Name>.dll` | The shared library, for the host it runs on |
| `module.json` | `{"name": "<Name>", "source_sha256": "<sha256 of the .scr it was translated from, lower-case hex>", "translator_version": "<scr2native version>"}` |

`name` must equal the directory name and the library's stem. `source_sha256` ties the module to
the original it was made from, so a module is rebuilt when its `.scr` changes; it is not a
signature.

## 5. Checks and refusals

`ModuleLoader::verify` makes the checks below in this order and stops at the first that fails;
`ModuleLoader::load` makes the same checks before it maps the module, so none of the module's code
(static initializers included) runs unless it passes. A refusal is a `LoadError`: a `Refusal`
reason, the module name and a detail. `describe()` gives the message, `refused: <module>: ...`:

| Order | `Refusal` | Detail | Message |
| --- | --- | --- | --- |
| 1 | `kNotFound` | | `refused: <m>: not found` |
| 2 | `kNoManifest` | | `refused: <m>: no module.json beside the library` |
| 3 | `kBadManifest` | the field | `refused: <m>: module.json is invalid: <detail>` |
| 4 | `kNotLoadable` | the reason | `refused: <m>: not a loadable module for this host: <detail>` |
| 5 | `kNoAbiTag` | | `refused: <m>: no sfcop_module_abi version tag` |
| 6 | `kAbiMismatch` | what differs | `refused: <m>: version tag mismatch: <detail>` |
| 7 | `kForeignImport` | the symbol | `refused: <m>: imports <detail>, which is outside the scripting library and the C runtime` |
| 8 | `kNoEntryPoint` | the export | `refused: <m>: does not export <detail>` |

`kNotLoadable` is also the answer when the checks pass and the platform loader then fails to map
the library (`dlopen`, `LoadLibrary`); the detail is the platform's reason.

The detail of `kAbiMismatch` names the field and both values, the module's first: `scripting
library version 21.0, expected 22.0`; `compiler ABI x86_64-windows-msvc, expected arm64-macos-itanium`.

## 6. What the loader does after the checks

`load` maps the library, resolves `MissionSpecEntry` and `ScriptEntry`, and returns them with the
manifest and a `ModuleId`. The game calls `MissionSpecEntry(kScriptVersion)` and `ScriptEntry()`
exactly as it calls the original `.scr`'s exports. `unload` releases the module; the caller has
dropped every pointer the module gave it first. A module is loaded at most once at a time.

## 7. Changing this contract

The contract is a hotspot. A change that a module built to the previous version cannot meet bumps
`kModuleContractVersion`, which refuses every older module until it is rebuilt.
